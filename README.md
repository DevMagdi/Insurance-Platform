# Insurance Brokerage Complaint Management

Arabic-first insurance complaint platform. **[PROJECT_BRIEF.md](docs/PROJECT_BRIEF.md) is the product source of truth.** The backend implements Phases 1–4, including scoped integrations, AI review, public APIs and voice-job flows; remaining customer/staff workflow screens, complete English editorial coverage, and production provider rollout remain unfinished. See the [architecture](docs/ARCHITECTURE.md), [ERD](docs/ERD.md), [implemented HTTP OpenAPI](docs/openapi.yaml), the [future-route roadmap](docs/openapi-roadmap.yaml) and the [deployment runbook](docs/DEPLOYMENT.md). The old `/api/v1/*` roadmap paths are **not** live routes.

## What's implemented

- **Authentication:** 5-minute single-use, five-attempt mobile OTP (Redis rate limits by mobile/IP); customer registration/identification; staff Argon2 sign-in, 48-hour emailed invitations and mandatory password change; optional TOTP enrollment and admin-required individual/global 2FA; signed, short-lived JWT access and rotating refresh cookies with replay-family revocation; double-submit CSRF for authenticated writes, logout and session list/revoke.
- **Access:** `resource.action` permission guards on staff HTTP routes, role union plus deny-wins per-user overrides, company/type/ownership `AccessScope` on complaint repository reads **and** PostgreSQL RLS on the same `SET LOCAL` transaction. Versioned Redis snapshots with DB token-version/session rechecks, access-change audit, delegation limits, last-administrator protection and `/api/me` effective access. The WebSocket checks origin and repeats authentication, permission and scope on each snapshot. IDs are masked; staff reveal requires a dedicated permission, reason and audit entry.
- **Complaints:** Egyptian national-ID and mobile validation; strict input, supported insurer/type and policy-number validation; atomic 24-hour idempotency and unique tickets; scoped lists, full-text search, combinable filters, counters, detail, timeline, CSV export (staff), replies/internal notes, status changes, limited reopening and CSAT. Guest tracking requires **both** ticket and national ID and returns only public status metadata. Customer actions, staff changes, exports and ID reveals are audited.
- **Files & notices:** 5-file/25 MB upload plans, 10 MB per file, short-lived signed one-use uploads, MIME sniffing/size/checksum checks, private S3-compatible storage, pending virus-scan state and *clean-only* scoped signed downloads. Transactional creation/status/reply notifications go to an outbox; a separate, table-blind `app_worker` DB login processes delivery and scan hooks. Unconfigured scanners never mark a file clean; unconfigured outbound providers do not pretend delivery succeeded.
- **Foundation:** PostgreSQL 16 partitions and indexes, seventeen Alembic revisions, a 33-key permission catalog, typed SQLAlchemy mappings, PgBouncer transaction pooling, Redis, Docker Compose/MinIO/Mailpit, 5,000-ticket opt-in synthetic seed, CI/CD with published container images, a React/Vite/Tailwind RTL shell plus Phase 5 frontend foundation. Implemented routes are under `/api/*`, not `/api/v1/*`.

**Phase 3 (backend):** Permission- and scope-filtered staff filters/search/workspace, assignment/reassignment, bulk status/assignment, escalation, merge/duplicate suggestions, saved views and private notifications. Rule-driven auto-assignment supports round-robin, least-workload and by-company strategies (company or agent targets, opt-in per rule) through restricted worker functions. The SLA engine honours per-rule calendars (IANA time zone, weekly working windows and holidays), per-rule alert lead time, response and resolution clocks, at-risk warnings, breach detection and auto-escalation; `POST /api/staff/admin/sla-rules/simulate` and `.../business-hours/preview` show the deadline a rule would set, and `GET /api/staff/complaints/{id}/sla` exposes the live clock state. Analytics adds a scope-safe daily rollup materialized view (worker refresh, whole-UTC-day requests only, automatic live-query fallback), SLA metrics and first-response timing on top of the Redis scope-hash cache. Administration covers user lifecycle (invite/edit/deactivate/reactivate/force logout/reset/2FA policy), roles with a permission matrix and clone, per-user overrides and scopes, effective-access explanation, companies/categories/SLA rules/templates, **provider integration settings that accept only vault secret references**, assignment rules with dry-run preview, the audit viewer (JSON/CSV/Excel), duplicate-candidate review and **scheduled email reports** (cron + time zone, relative window, CSV or Excel attachment, owner reauthorization on every run, run history, automatic disable after three failures). Async exports now render **CSV, Excel or PDF** with the same worker-only path, per-attempt keys, 1,000-ticket/2 MB limit, 15-minute expiry and *per-row scope reauthorization at download*.

**Phase 4 (backend):** The SQL-backed integration queue is idempotent, retries with backoff, dead-letters exhausted jobs, rechecks sender permission and ticket scope at claim time, and encrypts credentials and payloads with AES-GCM. Admin endpoints connect/disconnect SMTP, SendGrid, SES, WhatsApp Cloud, IMAP, OpenAI-compatible LLM, Twilio/Vonage voice and mock providers; webhook signing secrets and API-key permissions/company scopes are managed separately. Email supports localized AR/EN templates, insurer forwards with clean ticket-scoped attachments, customer replies, ticket-matched IMAP/webhook inbound messages and delivery-status events. WhatsApp supports approved templates, opt-in enforcement, the 24-hour same-ticket free-text window and delivery/read callbacks. A unified inbox combines portal, email, WhatsApp, calls and timeline events. AI analysis masks national IDs/contact PII, encrypts insights, and requires a recorded human approval before a suggested reply can be sent. Voice jobs require stored customer consent, support scheduling, Twilio/Vonage outbound adapters and signed status callbacks, and persist minimized transcripts plus encrypted private recordings in call logs. Mock-provider tests cover the external boundaries.

**Still unfinished / production gates:** complete staff/customer workflow screens, demo lead capture, dedicated push delivery beyond scoped WebSocket/polling, payment providers, live-provider end-to-end verification, deployment/observability/load and independent security reviews, real backups and PDPL review. Email/SMS remain **Mailpit-only in development** (`DEV_SMS_MAILBOX=true`); configure and verify real providers before production. The voice inbound conversation path currently relies on normalized callbacks and the working mock; complete vendor-specific IVR/STT/TTS rollout separately. Production antivirus is also unconfigured. Never expose an unscanned attachment as clean. Capacity of 1,000,000 concurrent users is a **target**, not a measured capability of this Compose stack.

The Phase 4 migration is exercised by the CI PostgreSQL 16 + PgBouncer testcontainers job. Local SQL/PL/pgSQL parsers provide syntax checks only; they do not replace real database execution.

- **Phase 5 frontend:** generated OpenAPI TS client, React Router, TanStack Query/Zustand/i18n, permission-aware views, access refresh, Arabic-first RTL, dark/light, component library, marketing landing, OTP/staff/MFA/invite, complaint intake and signed-in customer portal (history/timeline/replies/reopen/CSAT/attachments), staff complaint details with scoped attachments, asynchronous human-reviewed AI suggestions and voice follow-up scheduling, plus PWA shell. See `docs/PHASE5_FRONTEND.md` for integration gaps.

## Local development (Docker Compose v2)

1. `make init` creates a git-ignored mode-0600 `.env` with random development secrets (refuses to overwrite). For demo accounts set a **local-only**, 12+ character `DEMO_STAFF_PASSWORD` in `.env`; never commit the file.
2. `make up` starts PostgreSQL, PgBouncer, Redis, MinIO/private bucket, Mailpit, migrations, API, worker, Vite and Nginx. Open `http://localhost:8080/`; API liveness `/api/health/live`, readiness `/api/health/ready`, browser API docs `/docs` via the API server. Mailpit UI: `http://localhost:8025/`, MinIO console: `http://localhost:9001/` (local ports). Direct PostgreSQL: `localhost:5432`; PgBouncer: `localhost:6432` (bound only to localhost).
3. `make seed` optionally inserts four insurers, roles and scoped demo staff, and ~5,000 tickets. It is idempotent. Demo staff must change their password at first login; the password-change challenge does **not** give access to protected staff endpoints. Never seed a production database.
4. `make partitions` prepares current/upcoming UTC monthly partitions. `make down` retains data; `docker compose down -v` **destroys local data**. Changing `POSTGRES_DB` after the first boot requires a new *development* data volume (init scripts only run on an empty volume).

`make init` creates the 32-byte `APP_ENCRYPTION_KEY`; keep it private and stable across API and worker containers because integration credentials, queued PII payloads, AI insights, transcripts and call recordings depend on it. Rotating it requires an explicit decrypt/re-encrypt procedure; simply replacing it makes existing ciphertext unreadable.

Use same-origin `/api/...` requests from the browser. A successful OTP verification or staff sign-in sets HttpOnly `access_token` (15 min by default), HttpOnly `refresh_token` (rotated via `POST /api/auth/refresh`), and readable `csrf_token` cookies; send `X-CSRF-Token` equal to that cookie on protected POST/PUT/PATCH/DELETE requests, including refresh. Cookies are Secure by default; use HTTPS outside the browser's localhost development exception. **Never log or put tokens/OTPs/national IDs in URLs** (except single-use invitation/reset links in private email). Example customer flow: `POST /api/auth/customer/otp/start`, read the local development OTP in Mailpit, `POST /api/auth/customer/otp/verify`, then `POST /api/customer/complaints` with `Idempotency-Key`, CSRF header and a valid complaint body; `GET /api/customer/complaints` returns owned tickets. A nonlogged-in visitor can `POST /api/guest/track` with `ticket_no` and `national_id` only.

Some useful implemented routes (see [OpenAPI](docs/openapi.yaml) for request schemas):

| Area | Paths |

The Compose worker intentionally has no scanner implementation, so local uploads stay pending unless an authorized scan verdict is recorded in a disposable test environment. Email invitations use Mailpit locally. A production rollout needs a real SMS/AV provider, HTTPS, a service-specific secrets store and independent security review.

## CI/CD

Every pull request and push runs `.github/workflows/ci.yml`: Ruff + format check, strict mypy, offline pytest with an 80% coverage gate, frontend lint/typecheck/Vitest/build, a **container job** that builds the API and web images, boots them together and fails if the built image's contract drifts from `docs/openapi.yaml`, and a `postgres-rls` job that applies all Alembic revisions to real PostgreSQL 16 behind PgBouncer, proves RLS, and seeds 5,000 tickets twice for idempotence.

`.github/workflows/cd.yml` runs on `main` and on `v*` tags: it publishes `ghcr.io/<owner>/insurance-platform-api` and `ghcr.io/<owner>/insurance-platform-web` tagged with the commit SHA, smoke-tests the **published** images end to end (SPA served, `/api/health/live` reachable through the web proxy, image contract equal to the committed OpenAPI), re-renders `docker-compose.prod.yml`, and only then optionally deploys over SSH — `pull` → `run --rm migrate` → `up -d` → readiness gate on `/api/health/ready`. Tag pushes additionally publish a GitHub Release. **Deployment is opt-in**: it needs the repository variable `DEPLOY_ENABLED=true` and the environment secrets `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY` (plus `DEPLOY_SSH_KNOWN_HOSTS` to pin the host key); when it is not enabled the job is skipped and the run summary says so. `make images`, `make prod-config`, `make deploy`, `make release VERSION=v1.2.3` wrap the same paths.

Production runs the pulled images via [`docker-compose.prod.yml`](docker-compose.prod.yml) — Postgres, PgBouncer (transaction pooling), Redis, MinIO, migrations as a one-shot container, then api/worker/web with health checks, log rotation and exactly one published port. Credentials live only in an on-host `.env.production` (mode 0600); the API and worker containers never receive the admin URL or the Postgres superuser password. See the [deployment runbook](docs/DEPLOYMENT.md) for host preparation, rollback (a tag change) and backup drills.

## Tests and code quality

`make install` needs Python 3.11+ and Node 22+ and installs backend dev/test and frontend lockfile dependencies. `make ci` runs Ruff, strict mypy, backend pytest **with `--cov=app --cov-fail-under=80`**, ESLint, TypeScript, Vitest and the frontend build. `.venv/bin/pre-commit install` enables hooks. `PYTHONPATH=backend .venv/bin/python scripts/export_openapi.py` regenerates the implemented contract; the roadmap is intentionally separate.

`make test-integration` runs both legacy RLS/PgBouncer tests (requiring a **disposable, already-migrated PostgreSQL** and the three URLs below) and the PostgreSQL 16 + Redis **testcontainers** tests (requiring a Docker daemon). Testcontainers provisions its own disposable stack and migrates it; it skips, explicitly, when Docker is unavailable. The Phase 4 migration and queue/RLS assertions are included in that PostgreSQL suite. Do not point integration test URLs at production databases.

```text
TEST_DATABASE_ADMIN_URL=postgresql+psycopg://postgres:...@localhost:5432/insurance
TEST_DIRECT_DATABASE_URL=postgresql+asyncpg://app_runtime:...@localhost:5432/insurance
TEST_PGBOUNCER_DATABASE_URL=postgresql+asyncpg://app_runtime:...@localhost:6432/insurance
```

`cd frontend && npm run api:types` regenerates OpenAPI types from `docs/openapi.yaml`. `make ci` passed locally on the upstream Phase 4 branch (Ruff/format, mypy, 152 backend tests at 81.27% coverage, frontend lint/typecheck/test/build). Docker is unavailable in this sandbox, so the migration/RLS testcontainers cases were not run locally; SQL parser checks are not proof of PostgreSQL behavior. The GitHub PostgreSQL CI job provisions PostgreSQL 16, PgBouncer, Redis and Docker testcontainers, applies every migration, runs the RLS/integration suite and checks seed idempotence. Check the PR status before deployment.

**Phase 5 remaining frontend integration gates:** the demo form currently needs a backend lead-capture route; attachment selection is not yet connected to the secure plan/upload flow; and AI/voice/integrations and operations features still need dedicated screens. The localized English copy, real provider verification, browser end-to-end tests and accessibility audit are also outstanding.

## Security and scale boundaries

`app_runtime` is neither table owner nor BYPASSRLS, while `app_worker` has **no direct table privileges**. Authenticated transactions install `SET LOCAL app.user_id` / `app.scope`; queries also apply `AccessScope` so ID guessing, search filters, exports, child records, notifications and WebSockets inherit the caller's scope. National IDs are AES-GCM encrypted with separate HMAC blind indexes; default detail responses only contain a masked suffix. See the [access-control ADR](docs/adr/0002-access-control.md), [PII ADR](docs/adr/0004-pii-and-channels.md) and the [Phase 3 SLA/report/rollup ADR](docs/adr/0006-phase3-sla-reports-and-rollups.md). Production needs TLS termination, key rotation, real provider integrations, backup/recovery testing, PDPL compliance review, load tests, PgBouncer/read-replica sizing and monitoring before any scale claim.
