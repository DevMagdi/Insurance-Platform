# ADR 0002: Effective access and RLS

**Status:** accepted (Phase 1 schema); command authorization/instant revocation middleware is next-phase work

**Decision.** Catalog keys are `resource.action`; custom/system roles grant permissions, a per-user `deny` overrides `allow`, and `allow` overrides role union. Staff must be `active`. For every complaint, intersect (a) effective `complaints.view`, (b) company grant (specific row or explicit `all_companies`), (c) optional insurance-type rows (empty = unrestricted), and (d) one required ownership level: assigned to me / a team of which I am a member / all. A missing company or ownership grant denies everything. Admins are scoped too (seeded with all companies/all ownership). Customer rows require the authenticated customer ID; public child rows only. Child-table RLS rechecks the complaint *at read time*, so access changes immediately hide old messages, attachments, calls, notifications, audit entries, search results and exports queried with the runtime role.

The API must authenticate/authorize each command by explicit permission and enforce actor scopes in services. Anti-escalation for future `users.manage_access` mutations: compute actor **effective** permissions and scope from the DB (not submitted UI values); no actor may grant a permission or data scope they do not hold, alter their own role/scope/overrides, deactivate the last active administrator, change a system role, or bypass a deny. Within one serializable transaction lock target, persist before/after in `access_change_log`, increment target `token_version`, invalidate refresh tokens/cache/websocket subscriptions, then publish revocation. Implement a server-computed effective-access preview (and compare before/after) before this UI is exposed. These mutation workflows are **not implemented in Phase 1**.

**DB boundary.** `app_runtime` is nonowner/non-BYPASSRLS; FORCE RLS also prevents accidental owner bypass. The API installs `SET LOCAL app.user_id` and `app.scope` *only after authentication* inside every transaction. Custom GUCs are not cryptographically authenticated by PostgreSQL; if an attacker can run arbitrary SQL as `app_runtime`, they can forge an ID. Never expose SQL to clients, disallow unsafe raw interpolation, and use parameterized queries plus least-privilege DB credentials. SECURITY DEFINER functions belong to a trusted migrator with BYPASSRLS (the Postgres superuser in local dev), never to the runtime role, and use a fixed search path. FORCE RLS means even an ordinary table owner cannot bypass policies; the migration checks this precondition so child-table lookups cannot recurse. Out-of-scope lookups return no rows; no GUC or invalid GUC fails closed. The runtime role has no direct table permissions on scope internals, no DELETE on tickets/audits, and no SELECT on national-ID bytes.

**Trade-off.** Per-row scope checks are more expensive than a broad WHERE filter; filter predicates/indexes and partition pruning remain necessary. RLS is a final backstop, not a substitute for server authorization, row ownership checks on mutations, audit, rate limiting or tests.
